# Midterm Mastery: experiment log

This is a live record of the fresh experiment series started on November 1, 2026. Times below are UTC; on this date Eastern Standard Time is UTC−5. Earlier October experiments are separate and must not be mixed into these runs.

## Setup and measurement

- AWS region: `us-east-1`; S3 object: `s3://midterm-mastery/tmp/tiny.txt` (65 bytes). A download through the gateway matched the local test file's SHA-256 hash.
- ECS image tag for the first experiments: `20261101212043`. Gateway and backend scaling limits were set to 2–2 tasks; simulated UDP send and receive loss were both initially 0%. Retry settings were the service defaults. The Locust workload uses `GET /files?name=tiny.txt`, a one-second wait, and closed-loop users.
- Locust 2.37.9 supplies the client-side request counts, failures, response times, and throughput. A local Prometheus exporter scrapes the Locust API every five seconds; Grafana visualizes those **client-side** data. CloudWatch separately supplies ECS CPU/memory and ALB metrics. A local recorder saves ECS desired, running, and pending task counts roughly every 30 seconds.
- The first exporter version passed through Locust's stale recent request rate while Locust was stopped. This affected the idle portions of earlier Grafana charts (notably between the send-loss and receive-loss runs). The exporter was corrected before the autoscaling experiment to show zero request/failure rate while stopped; active-run Locust CSVs and measurements were not changed. Do not interpret the earlier idle Grafana rate as real traffic.
- Existing backend logs record individual simulated incoming/outgoing datagram drops and overload messages; gateway logs record missing-chunk retry messages. The logs do **not** provide a complete count of all OPEN retries. Export logs before destroying the CloudWatch log groups.
- Terraform initially reported an empty result reading the gateway scaling policy. AWS and Terraform state both subsequently showed the expected policy; its taint was removed after confirming it existed. The two services reached two running tasks and `COMPLETED` deployments before the load started.
- The Locust/Grafana counters were reset between measurement stages; Grafana's time series preserves the load history. Locust Statistics values for each stage are cumulative from that stage's reset. Saved CSVs preserve the individual snapshots.

Screenshots: `load-recovery-stats.png`, `load-recovery-charts.png`, `load-recovery-grafana.png`. The earlier 102-request snapshot is also retained in `results/load-recovery-5.csv`.

Preliminary observation: with these fixed task limits and this small file, the 20-user stage had higher latency and throughput than the 5-user baseline. In the recovery snapshot, latency returned close to the original baseline. This is an observation for the measured run, not a general capacity claim.

CloudWatch evidence: `screenshots/load-cloudwatch-cpu-aws-widget.png` and `screenshots/load-cloudwatch-requests-per-target-aws-widget.png` were rendered by AWS `GetMetricWidgetImage`, rather than captured from a browser. ## Experiment 3: autoscaling response (0% loss)

The backend was rolled to task definition revision 9 with send and receive loss both reset to 0%. Both scaling targets were restored to a minimum of 2 and maximum of 4 tasks. The gateway policy targets 100 ALB requests per target per minute; the backend policy targets 60% CPU. The ECS task recorder showed two running gateway and two running backend tasks with completed deployments immediately before the gradual ramp.

The gradual trial requests 5 users, then 20, then 50, holding the 50-user plateau for at least three minutes. Locust's counters reset after each user target is reached, so stage CSVs describe individual plateaus; Prometheus keeps the surrounding time series. The 5-user measurement began at `2026-11-02T03:27:36Z`, the 20-user measurement at `03:28:46Z`, and the 50-user measurement at `03:29:54Z`. Stage-change requests and measurement start times are saved in `results/events.jsonl` and `results/run-manifest.csv`.

During the first three minutes at 50 users, `results/autoscale-ramp-50-minute-3.csv` recorded 1,345 requests, 627 HTTP failures, 7.32 requests/s, 6.9 s median, and 7.6 s p95. These response-time statistics include failed requests. A CloudWatch snapshot reported a recent ALB RequestCountPerTarget value of 223 requests/target/minute. The generated gateway high alarm was configured for three 60-second evaluation periods above 100; the low alarm had 15 periods below 90. Scaling activity requested four gateway tasks at `03:34:35Z`; the recorder saw desired=4/running=2/pending=2 at `03:34:50Z` and running=4 at `03:35:21Z`. Backend tasks remained at two in these samples. A target-health check subsequently confirmed all four gateway targets healthy.

The user-provided `autoscale-ramp-stats.png`, `autoscale-ramp-charts.png`, and `autoscale-ramp-grafana.png` screenshots were captured before the scale-out request. A separate 50-user post-scale measurement started at `03:36:50Z` after all four targets were healthy. The first 60-second snapshot `results/autoscale-ramp-after-scale.csv` contains 488 requests, one HTTP failure, 7.79 requests/s, 6.3 s median, and 7.3 s p95. The final snapshot `results/autoscale-ramp-after-scale-final.csv` contains 644 requests, one failure, 7.87 requests/s, 6.3 s median, and 7.2 s p95. Locust was confirmed stopped at `03:38:13Z`. These are sequential time windows from a single run; the change in error rate coincided with scale-out but is not proof that task count was the sole cause.

AWS-generated CloudWatch graphs for CPU and requests per target are in `screenshots/autoscale-ramp-cloudwatch-*.png`, with widget definitions in `results/`. The independently generated `figures/autoscale-ramp-task-counts.png` is a plot of the timestamped 30-second ECS DescribeServices samples, not a CloudWatch screenshot. The scaling activity export reports that the gateway scale-out to four completed successfully at `03:35:44Z`.

After the ramp stopped, the gateway high-load alarm was checked and had returned to OK. At `2026-11-02T03:42:48Z`, the gateway desired count was **manually** set to two to make the spike's starting capacity comparable without waiting for the 15-period scale-in alarm. This manual intervention must not be presented as an automatic scale-in result; wait for two running, healthy gateway tasks before the spike.

**Sudden spike:** the recorder showed gateway and backend both desired=2/running=2 at `03:43:10Z`; the gateway target-health check showed two healthy and two deregistering/draining targets. With no Locust users active before the trial, 50 users were requested at 25 users/second at `03:43:47Z`, and the separate 50-user statistics measurement began after reaching 50 and resetting counters at `03:43:54Z`. The first three-minute snapshot `results/autoscale-spike-50-minute-3.csv` has 1,497 requests, 777 HTTP failures, 8.19 requests/s, 5.6 s median, and 6.2 s p95; response times include failures. Scaling activity requested four gateway tasks at `03:49:35Z`; the recorder saw desired=4/running=2/pending=2 at `03:49:56Z` and running=4 at `03:50:28Z`. A target-health check confirmed four healthy gateway targets, and a separate post-scale sample started at `03:51:06Z`: `results/autoscale-spike-after-scale-final.csv` contains 492 requests, 0 failures, 8.20 requests/s, 5.8 s median, and 7.6 s p95. Locust was confirmed stopped at `03:52:09Z`. Screenshots `autoscale-spike-stats.png`, `autoscale-spike-charts.png`, and `autoscale-spike-grafana.png` were taken before the scale-out request. The draining targets are a starting-condition difference from a fully settled two-target group and must be considered when comparing trials.
